## 🔎 What This Document Covers

This document describes how Personal Log Manager Client at https://github.com/hmlendea/personal-log-manager-client handles personal data. It covers the application behaviour and verified integrations described below. Where the software is self-hosted, the instance operator may have separate responsibilities described below.

## 🏠 Self-Hosted Deployments

This document covers both the project maintainers' practices and self-hosted instance operators. Operators control their instance's configuration, local storage, logs, backups, access controls, retention, and request handling unless the project directly controls those functions.

The application sends the following data from a self-hosted instance to external services:
- API requests to the configured Personal Log Manager API instance (base URL set in `appsettings.json`) — includes the user's API key as bearer authentication and a client identifier containing the machine name (`Environment.MachineName`)
- No telemetry, crash reports, update checks, or other data are sent to project maintainers or external monitoring services

Operators can disable the external API flow by not configuring a `personalLogManager.baseUrl` or by restricting network access from the server process to the API endpoint.

## 📥 Data We Handle

### Data Provided to the Application

- API key — entered by the user in the browser UI on first launch; stored in browser local storage
- Locale preference — selected by the user (English or Romanian); stored in browser local storage

### Data Generated or Collected by the Application

- Rate-limiting state — failed API key attempt timestamps and lockout expiry; held in server memory per circuit scope, not persisted
- Antiforgery tokens — generated by ASP.NET Core middleware for request validation; standard framework behaviour
- Server logs — standard ASP.NET Core request/response logging (if enabled by the operator); may include request paths, timestamps, and IP addresses

### Data Received from Integrations

- Log entries — retrieved from the configured Personal Log Manager API; includes log ID, date, time, time zone, and structured entry data
- API error responses — authentication failure or unauthorised codes from the upstream API

## 🧭 Processing and Use

The application processes the data described above for these verified functions:
- Authenticating API requests — API key
- Identifying the client instance — client identifier containing machine name
- Retrieving log entries for a date — log entries from upstream API
- Searching log entries by text — log entries from upstream API
- Viewing, creating, editing, and deleting log entries — log entries and API key
- Storing user preferences — API key and locale in browser local storage
- Enforcing rate limits on failed authentication — rate-limiting state

## 🗄️ Storage, Retention, and Deletion

| Data category | Storage location | Retention | Deletion control |
|---------------|------------------|-----------|------------------|
| API key | Browser local storage (client-side) | Until user clears it or browser storage is cleared | User can clear via UI or browser settings |
| Locale preference | Browser local storage (client-side) | Until user changes it or browser storage is cleared | User can change via UI or browser settings |
| Rate-limiting state | Server memory (per circuit) | In-memory only; cleared on circuit end or lockout expiry | Automatic expiry; operator controls server restart |
| Antiforgery tokens | Server memory / cookie (ASP.NET Core) | Per session | Framework-managed |
| Server logs | Operator-configured log destination | Operator-defined | Operator controls log rotation and retention |
| Log entries | Upstream Personal Log Manager API | Upstream API policy | Upstream API controls; this client only requests deletion via API |

For self-hosted deployments, the instance operator controls server logs, backups, and any server-side persistence. The project does not operate a central database or log store.

## 🔗 External Processing and Integrations

| Service or integration | Purpose | Data involved | Configuration or documentation |
|-----------------------|---------|---------------|--------------------------------|
| Personal Log Manager API | Authoritative personal log storage and operations | API key (bearer token), client identifier (machine name), log entry data | `appsettings.json` → `personalLogManager.baseUrl` |
| NuciAPI.Client 1.2.3 | HTTP request/response transport and API contract base types | Request/response payloads including authentication | NuGet package; see https://www.nuget.org/packages/NuciAPI.Client |

The application has no built-in external data transfer beyond the configured Personal Log Manager API.

## ⚙️ User Controls and Requests

The following documented controls or request procedures are available:
- Clear API key — use the browser UI or browser local storage settings
- Change locale preference — use the browser UI or browser local storage settings
- Request log entry deletion — use the delete button in the entry detail panel (dispatches request to upstream API)
- Operator controls server logs, backups, and retention — via server configuration and log rotation

## 🌍 International Transfers

Data may be transferred to the configured Personal Log Manager API instance. The deployment location of both this client and the upstream API is controlled by the instance operator. No data is sent to project maintainers or fixed external regions.

## 🛡️ Data Protection and Security

- API key is transmitted only to the configured Personal Log Manager API over HTTPS (when the upstream API uses HTTPS)
- API key never leaves the browser except in authenticated requests to the configured API
- Client identifier includes `Environment.MachineName`; operators should review whether this is acceptable for their deployment
- ASP.NET Core antiforgery middleware is enabled for the interactive host
- No server-side database or persistent log store is configured in this application
- For self-hosted deployments, the operator is responsible for:
  - Keeping the .NET runtime and dependencies updated
  - Managing secrets (API keys are client-side only)
  - Configuring access controls and network exposure
  - Protecting server logs and backups
  - Enforcing HTTPS in production

The original maintainers are not responsible for changes, modifications, or privacy issues introduced by downstream forks.
